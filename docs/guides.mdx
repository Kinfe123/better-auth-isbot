# Guides

After the initial setup, most day-to-day work with `better-auth-is-bot` involves tuning how the plugin behaves in your environment: adjusting which routes are protected, customizing the error response bots receive, and diagnosing why a request is being blocked or allowed unexpectedly.

The guides in this section cover those tasks with concrete examples drawn from the plugin's documented behavior. Each guide focuses on a specific outcome rather than restating the configuration reference.

## How the plugin handles requests

Understanding the order of operations helps you reason about most runtime questions without additional tooling. When a request arrives at your better-auth instance, the plugin applies these steps in sequence:

1. **Request filtering** — only `POST` and `GET` requests are checked; all other HTTP methods pass through without inspection.
2. **Route matching** — if `protectedEndpoints` is set, the request path is compared against those patterns (wildcards are supported). If no list is provided, all routes are treated as protected.
3. **Bot detection** — the `User-Agent` header is analyzed using the [`isbot`](https://www.npmjs.com/package/isbot) library.
4. **Response** — a detected bot on a protected route receives a `400 Bad Request` response.

Keeping this sequence in mind is usually enough to trace why a particular request is being blocked or allowed.

## Customize the error response

By default the plugin returns a generic error body. You can replace the message with something specific to your application:

```typescript
import { betterAuth } from "better-auth";
import { IsBot } from "better-auth-is-bot";

const auth = betterAuth({
  plugins: [
    IsBot({
      errorMessage: "Access denied for automated requests."
    })
  ],
});
```

The `errorMessage` value is returned inside the JSON body of the `400` response that blocked bots receive.
