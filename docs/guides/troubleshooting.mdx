# Troubleshooting

Most problems with `better-auth-is-bot` fall into one of three areas: the plugin not blocking bots when it should, the plugin blocking requests it should allow, or a misconfigured `errorMessage`. The sections below connect each symptom to its most likely cause.

## Bots are not being blocked

The plugin only inspects `POST` and `GET` requests. Requests using other HTTP methods pass through without any bot check. If you expect a different method to be blocked, that is by design — the plugin does not check those methods.

When `protectedEndpoints` is not set, every `POST` and `GET` route is checked. If you have provided a `protectedEndpoints` array, confirm that the route the bot is hitting matches one of your patterns. Wildcards like `/auth/*` match any sub-path under `/auth/`, but the pattern must cover the exact path being requested.

Bot detection is based on the `User-Agent` header analyzed by the `isbot` library. If the bot is sending a `User-Agent` that `isbot` does not recognise as automated traffic, the request passes through. There is no way to override the detection logic within this plugin; you would need to open an issue against the `isbot` package itself.

## Legitimate requests are being blocked with a 400

A `400 Bad Request` response means the plugin identified the `User-Agent` as a bot. Common causes:

- A server-to-server integration or test client sending a `User-Agent` string that `isbot` classifies as automated (for example, generic HTTP library defaults like `axios/1.x` or `python-requests/2.x`).
- A monitoring or uptime tool probing one of your protected routes.

To exclude specific routes from bot checking, pass them to `protectedEndpoints` rather than leaving that option unset. When `protectedEndpoints` is provided, only the listed paths are checked — everything else passes through untouched.

## Customising the error message

When a bot is detected the plugin returns a `400` response. If you need the message in that response to say something specific, set `errorMessage`:

```typescript
IsBot({
  errorMessage: "Access denied for automated requests."
})
```

Without this option the plugin uses its own default message. The response is always `400 Bad Request`; only the message body changes.

## Verifying the plugin is active

Run the test suite to confirm the package is correctly wired up in your project:

```bash
pnpm test
```

`vitest` will run the plugin's tests against a local SQLite database. A passing run confirms the plugin loads and that bot detection behaves as expected.

If you are iterating on configuration during development, `pnpm dev` runs `unbuild --watch` and rebuilds the package on every change, so you do not need to manually rebuild between edits.
